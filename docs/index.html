one program · one record · one check

A run is a claim you can check, and flow keeps the claim.

cancho-flow runs a program as a step and writes down what it was given and what came out. Later it tells you whether the files on disk still match.

How it works

A step is hashed, run once under limits and written down. The record is read back by a second program that cannot run anything.

In words: the step names a program and its files. flow step hashes the program and the inputs, runs the program from one baked directory, hashes the outputs and writes one record. flow-records lists, shows and checks records. A limit that is hit, a failed program or a false claim is refused with a rule tag, an exit code and a hint.

Two programs, four verbs

flow starts programs and holds a clock for the deadline only. flow-records only reads. Neither is a scheduler, a shell or a sandbox.

  • flow step
  • flow-records list
  • flow-records show
  • flow-records check

Try it

Build it from source. You need git, Rust, clang and python3, and the network for the clones and cancho install. The programs a step may start are the files of one directory baked into the binary, so you build your own.

git clone https://github.com/alpibrusl/cancho                     # the compiler, at the commit cancho.toml names
git clone https://github.com/alpibrusl/cancho-flow && cd cancho-flow
REV=$(sed -n 's/^cancho *= *"\([0-9a-f]*\)".*/\1/p' cancho.toml)  # the compiler these sources need
(cd ../cancho && git fetch -q origin && git checkout "$REV" && cargo build --release -p cancho)
export CANCHO=$PWD/../cancho/target/release/cancho PATH=$PWD/../cancho/target/release:$PATH
cancho install                                                    # fetches the pinned contract (network)
python3 scripts/flow_build.py --programs /opt/agent/programs --out build/flow --bin flow
python3 scripts/flow_build.py --programs /opt/agent/programs --out build/flow-records --bin flow-records

Then run the commands above, with your own programs in the directory. scripts/check.sh runs the authority check, the gates and every mutant.

The small print: what is checked, what is not, and what is missing

The same bytes

A record is a pure function of its inputs: the same step in another directory is the same file. The gate runs it twice and compares the bytes.

Refusals are data

One JSON line with a rule tag, an exit code and a hint. A program that fails, a deadline, a missing output and a false --deterministic claim each stop the step.

Authority you can read

What each program may touch is derived by the compiler (16 labels for flow, 7 for flow-records) and checked against a committed manifest. flow-records has no exec, no clock and no write.

Real output, replayed; it is not a live session. The demo is a log digest: scripts/site/digest counts the first column of access.log. What is cut: a hash shows 12 of its 64 digits, a timing is shown as N, and the long refusal lines keep the rule, message and hint (marked …). The programs run with an empty environment except PATH, so the output does not depend on the machine’s locale.

Limits. flow records what the caller declares: it cannot see a file a program reads or writes without being told, and a secret in an argument is recorded (keep secrets in files named with --in, where only a hash is recorded). It is tested on Linux x86-64 only, so “the same bytes on every platform” is open. Not built yet: replay, compare, memoisation, --keep-output and plans (design, section 11). One user counts so far. No speed is claimed.
